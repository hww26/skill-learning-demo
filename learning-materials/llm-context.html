学习目标

  • 学完能够说清上下文窗口是什么：由哪几类内容构成、以什么单位计量、与输出预算的关系。
  • 学完能够解释"上下文为什么不能无限长"：自注意力的平方复杂度、"注意力预算"与 context rot 现象。
  • 学完能够描述 Lost in the Middle 现象，并据此对 RAG 检索结果的排布给出改进建议。
  • 学完能够列举管理上下文的实用手段：检索、压缩（compaction）、结构化笔记、子代理架构。

1. 个人理解解释

一句话大白话定义：上下文（context）就是大模型单次推理时"能看见、能拿来思考"的全部信息；上下文窗口（context window）就是这个"视野范围"的大小上限——超出窗口的内容，模型这次推理完全感知不到。

类比：模型是一张工作台。模型参数 = 你已经背熟的技能和知识（训练完就固定，不随任务变化）；上下文 = 你面前的工作台——桌面上摊开的资料、任务单、工具说明书，全部摆在你眼前供你随时翻看。工作台只有那么大：桌满了，摆不下的只能凭记忆答（参数知识，可能过时或记错），或者起身去书架取（检索/RAG/工具调用）。Anthropic 把这称为模型有限的"注意力预算"——像人的工作记忆，摊开的资料越多，摊在每份上的注意力就越少。

在 AI 技术版图中的位置

上下文是大模型应用的"主战场"：提示词工程（Prompt Engineering）管的是"往桌上放什么指令"；RAG 管"从书架取什么放上来"；多轮对话与 Agent 的记忆管理管"桌上东西怎么收拾、怎么腾地方"。2025 年起，Anthropic 把这套实践正式命名为上下文工程（context engineering）——提示词工程的演进形态：核心目标是在有限窗口内，找出最小化的高信号 token 集合来最大化模型表现。

2. 核心机制 / 组成

窗口里装什么

一次 API 调用的上下文通常由以下部分叠加而成（不同厂商实现细节以官方文档为准）：

┌─ 上下文窗口（一次推理的"全部视野"）────────────┐
│ system prompt   全局指令与人设                  │
│ 对话历史        历轮 user / assistant 消息       │
│ 检索内容        RAG 命中的片段、文件内容          │
│ 工具定义与结果  function calling 的清单与返回值   │
│ 本轮输入        用户刚说的话                     │
│ ─────── 输出预算（回复也在同一个窗口里生成）─── │
└──────────────────────────────────────────────┘

计量单位是 token（模型分词后的最小单元）：粗略地，1 个英文单词 ≈ 1.3 个 token，1 个汉字 ≈ 1~2 个 token——具体取决于各家 tokenizer，不要按字符数心算，要用官方计数器。输入与输出通常共享同一个窗口预算：窗口 128K 不代表能"读 128K 再写 128K"。

为什么上限不能随便加长

  • 平方复杂度（机制根源）：Transformer 的自注意力让每个 token 都与所有 token 两两交互（出自《Attention Is All You Need》，2017）——长度翻倍，注意力计算与显存约翻四倍，这就是长上下文"贵且慢"的底层原因。
  • 注意力稀释（效果根源）：Anthropic 在 2025 年的上下文工程博文中指出，受架构与"上下文腐烂"（context rot）影响，token 越多、每份信息分到的注意力越少——窗口标称再大，塞太满表现照样掉。

关键现象：Lost in the Middle

Liu et al.（TACL 2023）在多文档问答与键值检索实验中发现：模型对开头和结尾的信息利用最好，位于长上下文中部的关键信息极易被忽略——呈现 U 形曲线，即便是宣称支持长窗口的模型也存在。

工程启示：把最重要的指令和材料放开头或结尾；RAG 命中的片段按相关性排序时，别把最关键的那条埋在中间。

长上下文与上下文工程

各家通过位置编码扩展（如 RoPE 插值、YaRN）、KV Cache 复用等技术把窗口从数万 token 推到百万级（具体数字演进极快，以各模型官方文档为准）。但窗口变大 ≠ 问题解决——Anthropic 给长时程任务开出三招：压缩（compaction，把旧对话总结后重开窗口）、结构化笔记（agentic memory，用 NOTES.md/记忆工具把关键事实持久化）、子代理架构（sub-agent 深入探索后只把精炼摘要带回主上下文）。此外，ICL（上下文学习，in-context learning）本身就是"写进窗口的临时教学"：几个 few-shot 示例不更新任何参数，就能改变模型行为。

3. 真实落地应用场景

  1. 长文档问答与合同审阅
    把整份合同/长报告直接放入窗口让模型通读。实践中要配合两条：关键条款优先放窗口首尾（对抗 Lost in the Middle）；超长文档先检索定位再精读局部，而不是无差别全塞。
  2. 多轮对话的历史管理
    聊天记录逐轮增长，逼近上限后必须治理：滑动窗口截断、对旧轮次做摘要压缩、把用户关键偏好写入结构化笔记——这正是各家"记忆"功能的底层逻辑。
  3. RAG 与长上下文的组合
    两者不是替代关系：检索负责"挑重点+保时效"，长窗口负责"容得下"。Anthropic 在上下文工程博文中总结的 just-in-time 检索是好范式：Claude Code 不预载全部代码，而是用文件路径与 grep 按需加载相关文件，窗口里只留当前需要的。
  4. Agent 的长时程记忆
    跑几小时的智能体无法把全部历史塞进窗口：用压缩重开窗口、用文件/记忆工具持久化任务状态、用子代理分工探索——这三种手段已成为 Agent 框架的标准配置（同见 Anthropic 博文）。

4. 易混淆点 & 使用边界

四组最易混淆的对比

维度上下文（窗口内容）常被混淆成的东西
参数知识临时摆上桌的资料，每次调用重新装误当成"模型学会了"——训练进参数的知识才是永久的
跨会话记忆单次调用结束即清空（无状态）误以为模型"记得上次聊天"——记得住靠的是外部存储把历史重新装回窗口
有效长度标称窗口只是"装得下"误以为"装得下=用得上"——注意力稀释与 Lost in the Middle 让有效利用打折
长上下文 vs RAG直接读全量资料误以为互为替代——实践中是组合：检索挑重点，长窗口兜容量

使用边界与常见误用

  • 塞得进 ≠ 用得上：窗口从 128K 升到 1M，不代表把所有文档一股脑塞进去效果就更好——注意力预算有限、成本按 token 计费平方增长，仍应先检索再精读。
  • 长上下文不能替代 RAG：时效性知识（今天的新闻、最新库存）不在任何窗口里，必须外部检索；全量塞入还慢且贵。
  • 上下文 ≠ 跨会话记忆：模型的"记得你"全是工程手段（把历史/笔记重新装回窗口），底层每次调用都是白纸。
  • token 消耗错觉：汉字、代码、表格的 token 开销与字符数差异很大；多轮对话的历史会持续吃掉预算，长回复同样占窗口——设计时应给输出留足空间。
  • 数字演进极快：各模型的窗口大小、多模态计量方式频繁更新，引用时以官方文档最新版为准。

6. 核心思考题

  1. 在工作台类比里，"把资料全摆上桌"（长上下文）和"去书架按需取"（RAG/工具检索）各付出了什么代价？出现了什么信号时，你应该从前者切换到后者？（提示：成本曲线、注意力稀释、资料时效性）
  2. 多轮对话产品为什么不能靠"无限加长窗口"一劳永逸解决记忆问题？请至少从计算成本、注意力稀释、工程可控性三个角度各说一条。
  3. "全量塞窗口""检索相关片段""子代理读全文只回摘要"三种模式，在准确性、成本、隐私暴露面上各有优劣——若你设计一个分析公司内部敏感合同的系统，会怎么组合它们，为什么？

7. 自测小题（附答案）

先自己作答，再点开对照。覆盖本资料全部易错点。

第 1 题：上下文窗口以什么为单位计量？1 个汉字大约对应多少？心算 token 数可靠吗？
答案：单位是 token（分词后的最小单元）。1 个汉字约 1~2 个 token，英文单词约 1.3 个——只是粗略估计。解析：不同 tokenizer 差异很大（代码、表格、表情更特殊），准确计数必须用官方计数工具，不要按字符数心算。
第 2 题：为什么注意力计算量会随上下文长度平方增长？这带来了哪两类直接代价？
答案：Transformer 自注意力中每个 token 都要与所有 token 两两交互（Attention Is All You Need），序列长度翻倍 → 交互对数约翻四倍。解析：两类代价：① 计算与显存开销（更贵更慢）；② 注意力稀释——token 越多分给每份信息的注意力越少（Anthropic 称之为 context rot），效果不升反降。
第 3 题：Lost in the Middle 揭示了什么现象？对 RAG 系统的检索结果排布有什么工程启示？
答案：模型对长上下文开头和结尾的信息利用最好，中部的关键信息极易被忽略（U 形曲线）。解析：启示是把最关键的内容放在窗口开头或结尾；RAG 命中片段排序时避免把高相关片段埋进中部，必要时做重排（rerank）后首尾布置。
第 4 题：一次调用中，上下文窗口里通常包含哪几类内容？输入和输出共用窗口吗？
答案：通常包含 system prompt、对话历史、检索到的资料、工具定义与工具返回结果、本轮用户输入；输出预算与输入共享同一个窗口。解析：所以"128K 窗口"不等于能读 128K 再写 128K——历史越长，留给回复和工具结果的空间越小，这正是长对话需要压缩治理的原因。
第 5 题（判断）：既然已有模型支持百万级 token 窗口，RAG 检索很快会被淘汰。这句话对吗？
答案：错。解析：三个理由：① 塞得进≠用得上——注意力稀释与 Lost in the Middle 让全量塞入的效果打折；② 平方成本让"全量塞"又贵又慢；③ 时效性知识（最新新闻、实时库存）不在任何静态窗口里，必须外部检索。实践是组合：检索挑重点 + 长窗口兜容量 + just-in-time 按需加载。
