1. 个人理解解释

在我看来，三者的关系可以压缩成一个画面——Agent 是动手干活的"员工"，大模型上下文是他手边那张容量有限的"办公桌"，Skill 是放在档案柜里、做到哪一步才抽出来翻哪页的"专家手册"。员工再聪明，桌面就那么大，不可能摊开公司全部资料；手册再厚，也只有被拿到桌上的那几页才真正起作用。​

类比：新员工入职。把 Agent 想成一位刚入职的员工：他的"脑力"来自大模型（LLM），但每次思考时真正"摆在面前"的信息——入职手册的目录、和同事的聊天记录、刚跑出来的报表——都必须摊在那张办公桌（上下文窗口）上。桌子面积有限（注意力预算有限），塞得太满反而什么都看不清（context rot，上下文腐烂）。公司则把专业经验整理成一本本操作规程（Skill）：每本的封面和目录（元数据）钉在工位墙上，他扫一眼就知道什么时候该翻哪本；真接到对应任务，才把那一本的正文摊到桌上细读；正文里指向的附件和模板，用到了再去档案柜取。三样东西缺一不可：没脑子干不了活，没桌子没地方想，没手册不专业。

权威定义的锚点

三份 Anthropic 官方材料，恰好各给了一块拼图：
· 《Building effective agents》（2024-12）：Agent "本质上就是 LLM 在循环中基于环境反馈使用工具"——这定义了员工怎么干活；
· 《Effective context engineering for AI agents》（2025-09）：上下文是"边际收益递减的有限资源"，工程目标是"找到能最大化期望结果的最小高信号 token 集合"——这定义了桌子有多大、东西怎么摆；
· 《Equipping agents for the real world with Agent Skills》（2025-10）：Skill 是"指令、脚本与资源组成的文件夹"，靠渐进式披露按需加载，"能打包进 Skill 的上下文容量实际上不受限"——这定义了手册怎么写、怎么翻。

在 AI 技术版图中的位置

三者不是三个并列的功能模块，而是同一个系统的三个侧面：LLM 提供推理能力（引擎），Agent 把推理组织成"行动—反馈"循环（怎么干活），上下文是循环每一轮都必须经营的原材料（在哪干活），Skill 是突破窗口限制、按需注入专业知识的机制（凭什么会干）。可对照本仓库前三份资料：agent.html 讲"员工"，llm-context.html 讲"桌面"，skill.html 讲"手册"——本篇讲的是三者如何咬合成一台机器。

2. 核心机制 / 组成

三者的分工与对应物

角色一句话定位关键机制类比
Agent把"想"和"做"连成循环的执行者agentic loop：读上下文 → 决策 → 调用工具 → 观察结果 → 继续上岗干活的员工
大模型上下文模型的"工作记忆/工作台"，容量有限注意力预算（attention budget）、context rot、上下文工程（compaction、即时检索、笔记、子代理）面积有限的办公桌
Skill住在磁盘上、按需加载的"专家手册"SKILL.md（元数据+正文）+ 捆绑资源；三层渐进式披露档案柜里的操作规程

注意分工中的依赖方向：Agent 循环每一轮都"活在"上下文里——从上下文读入目标与历史，把工具结果写回上下文；而 Skill 的大部分内容不在上下文里，它是对有限工作台的外部扩充。三者的咬合关系是：循环制造信息 → 窗口装不下、装多了会"糊" → Skill 用渐进式披露把知识留在磁盘上，只把"当下这一步"需要的那一层送进窗口。

运行循环：上下文是每一轮的"现场"

while 任务未完成 且 未触发终止条件:
    # 上下文 = 工作台，每一轮都要重新"策展"
    思考 = LLM(系统提示 + 技能目录(元数据) + 对话历史 + 上一步观察)

    if 这一步需要专业知识:
        把对应 SKILL.md 正文读入上下文             # 渐进式披露 · 第二层
    if 还需要更多细节:
        把技能捆绑的参考文件读入上下文             # 渐进式披露 · 第三层

    行动 = 调用工具(读文件 / 检索 / 执行代码 / 调API)
    观察结果 → 写回上下文                          # 上下文逐轮增长

    if 上下文接近窗口上限:
        压缩摘要 / 写结构化笔记 / 派子代理隔离探索   # 上下文工程三件套
交付最终结果

每一轮循环都在改写上下文：读走信息做决策，写入新的工具结果。所以上下文不是静态的背景板，而是 Agent 每一步都要主动经营的稀缺资源——这就是"上下文工程"成为独立工程学科的原因。

Skill 如何"挤进"有限的工作台：渐进式披露

层级内容何时进入上下文占用情况
第一层 · 元数据SKILL.md 头部的 name + description启动时预加载，常驻系统提示极小（仅够让 Agent 判断"何时该用我"，描述字段有长度上限约束）
第二层 · 正文SKILL.md 的操作指引主体Agent 判断与当前任务相关时，主动读取文件中等，只在任务相关时存在
第三层 · 捆绑资源参考文件、脚本、模板等Agent 按需自主发现并读取可以很大，但只在用到的那几步进入窗口

正因如此，官方文章才说"能打包进 Skill 的上下文容量实际上不受限"——知识本体住在磁盘上，窗口里永远只出现它的当前需要的那一层。

3. 真实落地应用场景

案例 1 · Claude Code（编码智能体）：三者协作的教科书案例。项目说明 CLAUDE.md 预置进上下文；glob/grep 让模型在文件系统上即时检索（just-in-time retrieval），而不是把整个代码库塞进窗口；接近窗口上限时自动压缩（compaction），保留架构决策与未解决的 bug；复杂的并行探索交给子代理（sub-agent）——它们用干净的窗口干活，只带回 1,000–2,000 token 的精炼摘要。上下文工程的四种策略在一个产品里集齐。（来源：《Effective context engineering for AI agents》）
案例 2 · Agent Skills 开放标准与官方仓库：Claude 的文档创建能力（docx/pdf/pptx/xlsx）底层就是几个以"文件夹 + SKILL.md"形式安装的 Skill；元数据常驻系统提示，正文与捆绑资源按需读取。2025 年 12 月起 Agent Skills 成为开放标准（agentskills.io），同一份技能文件夹可跨平台移植。（来源：《Equipping agents…with Agent Skills》与 anthropics/skills 仓库）
案例 3 · Claude 玩《宝可梦》：Agent 在数千游戏步数中把关键状态写成结构化笔记持久化到上下文之外，窗口重置后读取自己的笔记继续训练数小时——说明"办公桌"之外还可以自建"档案柜"，这就是 Agentic Memory（代理记忆）。（来源：《Effective context engineering for AI agents》）
案例 4 · 本仓库自身：.workbuddy/skills/concept-learning-generator/ 就是一个项目级 Skill——Agent 平时只看得到它的 name + description（第一层），接到"生成学习资料"任务才读取 SKILL.md 正文（第二层）。learning-materials/ 里前三份资料与本篇，都是这套机制跑出来的结果。三者关系不在远方，就在你正在用的系统里。

4. 易混淆点 & 使用边界

易混淆一：上下文（Context） vs 长期记忆 / RAG 知识库

维度大模型上下文 Context长期记忆 / RAG 知识库
位置推理"现场"，模型直接可见窗口之外（文件、向量库、数据库）
生命周期随一次会话/一轮请求存在跨会话持久
容量有限（注意力预算，受 context rot 制约）近乎无限
进入方式天然就在，无需动作必须靠检索/读取"搬进来"

一句话：RAG 和记忆是给上下文"进货"的仓库，上下文才是货架——进了仓库不等于上了货架。

易混淆二：Skill vs 工具（Tool / MCP）

维度Skill工具 Tool / MCP
本质知识包：教 Agent "这类事该怎么想、怎么做的流程"接口：给 Agent "手"，连接外部世界（执行动作）
内容指令、流程、脚本、模板、参考文件函数/API 定义（名称、参数、说明）
占上下文方式三层渐进式披露，正文与资源按需加载工具定义常驻系统提示（每轮可见）

一句话：Skill 与工具不是竞争关系，而是"脑外知识"与"手"的关系——Skill 里经常教的正是"如何用好这一组工具"。

易混淆三：Agent vs Workflow（一句话回顾）

控制流由 LLM 现场决定的是 Agent；控制流被代码预先写死的是 Workflow。前者的灵活性与不可预测性是同一枚硬币的两面。

使用边界

  • Skill 不是自动生效的外挂：Agent 环境必须支持文件读取/代码执行；且 SKILL.md 的 description 必须写清"什么时候用我"——描述含糊，Agent 在第一层就错过了它，后面两层再精彩也不会被加载。
  • 不是所有任务都值得上"全家桶"：单轮问答用直接提示词即可；Anthropic 的建议是 do the simplest thing that works——复杂度只在可证明改善结果时才增加。
  • 上下文工程不是越省越好：过度压缩会丢掉"事后才显重要"的细节；官方建议先最大化召回率，再迭代提升精确率。
  • 窗口变大 ≠ 问题消失：即使百万 token 级窗口，context rot 依然存在——"最小高信号 token 集合"仍是指导原则，Skill 的按需加载逻辑不因窗口扩容而过时。

6. 核心思考题

  1. 上下文窗口正越做越大（百万 token 级）。如果窗口"无限大"，上下文工程和 Skill 的渐进式披露还有存在的必要吗？请用"注意力预算 / context rot"的机制（而不是窗口数字）论证你的结论。
  2. 假设你要为一个日程管理 Agent 编写"会议安排" Skill：哪些内容应放进 SKILL.md 正文（第二层），哪些应拆到第三层参考文件？你的取舍依据是什么？（提示：判断"相关"的频率 × 加载成本）
  3. 工具调用结果动辄上万 token，长任务的窗口必然告急：压缩（compaction）、写笔记（note-taking）、子代理（sub-agent）三种策略各自适合什么场景？如果强行只用其中一种，分别会出什么问题？
