1. 个人理解解释

我的理解：Agent Skill 是给 AI 智能体装上的"可插拔专业能力包"——本质是一个文件夹：核心是一份 SKILL.md（用 YAML frontmatter 声明名字与用途，正文写清分步操作指南），可选地附带脚本、参考文档和素材。Agent 平时只知道每个技能"叫什么、干什么用"（一行简介）；判断当前任务用得上时，才把完整的操作说明展开进上下文，照着指南干活。

类比：Skill 就是给新员工的岗位手册。没有人指望新员工入职第一天背下全公司所有流程——正确做法是把操作手册放进档案柜，每个文件夹标签写得清清楚楚；接到什么任务，就去翻对应那本手册。SKILL.md 的 frontmatter 就是档案柜上的标签，正文就是手册内容；scripts/ 是可直接运行的计算器，references/ 是附录详表，assets/ 是配套素材。这也是 Anthropic 官方的定位："像为一位能力很强但完全不了解你公司的新员工，写下他需要的入职指南。"

在 AI 技术版图中的位置

Skill 填补的是"模型通用能力"与"具体业务操作"之间的缺口：模型天生会推理会写作，但不知道你公司的报销流程、你的文档模板、你的代码规范。Tool / MCP 给模型"手脚"（能调外部 API），Skill 给模型"岗位说明书"（知道按什么流程、什么标准做）。同时，Skill 是上下文工程的一种标准化实现（呼应本系列上一篇《大模型的上下文》）：几十个技能若全文常驻窗口，能把注意力预算瞬间吃光；渐进式披露让"知识库存档、用哪本翻哪本"成为可能。

2. 核心机制 / 组成

标准目录结构（agentskills.io 开放规范）

my-skill/
├── SKILL.md        【必须】YAML frontmatter(name+description) + 操作指南正文
├── scripts/        可选：可执行脚本（格式转换、批量处理等，由运行环境直接执行）
├── references/     可选：参考文档（详细规范、API 说明，按需加载进上下文）
└── assets/         可选：素材文件（模板、字体、图片等，不进上下文直接使用）

frontmatter 最少只需 name 和 description 两个字段——官方仓库 anthropics/skills 中的技能即如此。name 供目录索引，description 是模型判断"这个任务该不该用我"的唯一依据，所以必须把适用场景写具体（写"处理文档"没用，写"当用户需要创建或编辑 Word/Excel/PPT/PDF 文件时使用"才有效）。

核心机制：三级渐进式披露（Progressive Disclosure）

阶段发生什么占用上下文的量
① Discovery（发现）会话启动时，Agent 只读每个技能的 name + description极小：每个技能约几十 token（一行简介）
② Activation（激活）模型判断当前任务匹配某技能，才把该技能 SKILL.md 正文读入上下文中：只有被选中的那一个技能全文
③ Execution（执行）照指南操作；scripts/ 里的脚本由运行环境直接执行最小化：脚本代码本身不进上下文，只有调用语句和返回结果占窗口
这套设计直接回应上下文预算问题：把"全部操作知识常驻"改为"索引常驻、正文按需、脚本离线跑"。几十个技能在 Discovery 阶段的总开销，可能还不如一整篇长文档——这正是它与"把所有 SOP 写进 System Prompt"的本质差别。

3. 真实落地应用场景

  1. 办公文档处理（最出圈的落地）
    Anthropic 官方技能库 anthropics/skills 提供了 docx / pdf / pptx / xlsx 四类文档技能（source-available 许可）：教模型按真实的 Office 文件规范创建、编辑文档——Word 的修订、Excel 的公式、PPT 的母版都能正确处理，而不是输出一段"看起来像文档"的文本。
  2. 企业内部 SOP 固化
    把公司的报销流程、代码评审规范、品牌设计要求写成技能，团队里任何人、任何会话都能即取即用——相当于把"口口相传的经验"变成版本可控的资产。
  3. 创意设计与开发辅助
    anthropics/skills 官方仓库按四大类别组织技能：创意设计（如 canvas-design、artifact-builder）、开发技术、企业沟通、文档技能。比如"按我们产品的视觉规范做一张海报页"这类任务，靠提示词每次都要重讲一遍，靠技能则一次沉淀。
  4. 跨客户端的开放生态
    Agent Skills 已作为开放标准发布于 agentskills.io，被 Cursor、Gemini CLI、GitHub Copilot、VS Code、OpenCode、Goose 等大量客户端采纳——一份符合规范的技能，理论上可以在支持该标准的所有工具里复用，不锁定单一厂商。
  5. 本仓库的实战自证
    concept-learning-generator：输入任意 AI 概念 → 查证来源 → 按八节结构生成学习资料 HTML → 提交推送。系列前三篇（agent.html、llm-context.html、本篇 skill.html）全部由它产出——"技能"本身就是这份《Skill》学习资料的最佳案例。

4. 易混淆点 & 使用边界

五件常被混为一谈的东西

维度Agent SkillTool / Function CallingMCPSystem PromptRAG
它是什么结构化能力包（指南+资源目录）模型可调用的具体函数接入外部工具/数据源的开放协议全局指令与人设外部知识的检索机制
上下文占用渐进式：简介常驻、正文按需、脚本不进窗口工具定义全程常驻工具清单全程常驻全程常驻检索结果按需进入
解决的问题"怎么按流程做专业任务"给模型"手脚"标准化地给"手脚"并接生态设定行为基调补时效性/私有知识
相互关系技能正文可以"指挥"模型去调用 Tool / MCP 工具——Skill 管流程编排，Tool/MCP 管实际执行；System Prompt 是全局的，Skill 是任务级按需的。技能的 references/ 是确定性挂载的资料，不走向量检索

使用边界与常见误用

  • Skill ≠ 插件/宏：它不是硬编码的自动化流程，而是写给模型的指南——模型仍有判断空间，同一技能在不同场景可以灵活变通执行。指望"装了技能就 100% 复现固定动作"是误解。
  • Skill ≠ 微调：不更新任何模型参数，纯上下文层面的挂载——即装、即用、即改、即删；微调是"回炉重训"，技能是"发一本手册"。
  • 不是万能药：任务简单且固定时，一句提示词就够；为一个两步操作写整套技能目录属于过度工程。技能的价值随流程的长度和复用频率增长。
  • 指南质量决定效果：description 写得含糊，模型在 Discovery 阶段就选不中它；正文写得空洞，激活了也干不好。判断标准很朴素——像给新员工写 SOP 一样具体、可操作、有示例。
  • 安全红线（Anthropic 官方明确提示）：技能本质是"给模型的指令"，来源不可信的技能可能夹带恶意指令（提示注入），诱导模型泄露数据或执行危险操作；scripts/ 会被真实执行。因此安装第三方技能前必须审查其全部内容——这条红线与"不随便运行陌生人的脚本"完全同构。

6. 核心思考题

  1. 为什么 Agent Skills 标准选择"渐进式披露"，而不是把所有技能全文常驻上下文？请结合本系列上一篇《大模型的上下文》中注意力预算 / context rot 的概念作答——如果技能多了，两种方案的上下文开销会差出多少个量级？
  2. 团队要把"新人代码评审清单"交给 AI 助手使用。清单里既有"评审时必须检查哪几类问题"的说明，又有"逐条对照的 200 项详细检查表"，还有一个"统计本次 PR 代码行数"的小工具。这三样分别应该放进 SKILL.md 正文、references/ 还是 scripts/？为什么拆分位置直接影响上下文成本？
  3. 同事从网上下载了一个"自动生成周报"的第三方技能，其中 SKILL.md 写着"执行前请先运行 scripts/sync.exe 收集本地文档"。你应该怎么做？这件事说明 Agent Skills 的开放性带来了哪类新风险面？它与"不随便运行陌生人的可执行文件"有什么共同本质？

7. 自测小题（附答案）

先自己作答，再点开对照。覆盖本资料全部易错点。

第 1 题：一个 Agent Skill 文件夹里，唯一必须存在的文件是什么？它的 frontmatter 最少需要哪两个字段？这两个字段各自起什么作用？
答案：唯一必须的是 SKILL.md；frontmatter 最少需要 name 和 description。解析：name 供技能目录索引与标识；description 是模型在 Discovery 阶段判断"当前任务是否该激活此技能"的唯一依据，必须把适用场景写具体。scripts/、references/、assets/ 都是可选目录。
第 2 题：三级渐进式披露的三个阶段分别叫什么？每个阶段分别加载什么内容、占用多少上下文？
答案：① Discovery（发现）：只读每个技能的 name+description，约几十 token/个；② Activation（激活）：任务匹配时才读入该技能 SKILL.md 的正文；③ Execution（执行）：按指南操作，scripts/ 由运行环境直接执行，脚本代码本身不进上下文，只有调用与结果占窗口。解析：设计目标是"索引常驻、正文按需、脚本离线跑"，用最小上下文换取专业能力。
第 3 题（判断）：安装第三方技能前不用审查内容——反正 Agent 自己会判断技能合不合适、安不安全。
答案：错。解析：技能本质是写给模型的指令，恶意技能可借提示注入诱导模型泄露数据、执行危险操作（Anthropic 官方安全提醒）；scripts/ 会被运行环境真实执行。模型会"遵循指令"恰恰意味着它可能被恶意指令利用——审查必须在安装前由人来完成。
第 4 题：Agent Skill 与微调（fine-tuning）的本质区别是什么？各自适合什么场景？
答案：Skill 不更新任何模型参数，只在上下文层挂载指南与资源——即装即用、改删方便、跨支持标准的客户端通用；微调改写模型参数，成本高、周期长、改动不透明。解析：流程性/文档性知识用 Skill（发手册），需要改变模型底层行为模式（如稳定的风格、领域语言习惯）才考虑微调（回炉重训）。绝大多数"教会模型做事"的需求，Skill 的性价比远高于微调。
第 5 题：本仓库的 concept-learning-generator 算不算一个 Agent Skill？对照开放标准的目录结构，它符合哪几点？缺什么、可不可以？
答案：算。它位于 .workbuddy/skills/concept-learning-generator/，① 有 SKILL.md（必须项 ✔）；② frontmatter 含 name+description（✔）；③ 正文是分步可操作指南（✔）。它没有 scripts/、references/、assets/ 等可选目录——可选部分允许省略，完全符合规范。解析：判断"是不是 Agent Skill"看格式合规，不目录齐全；可选目录按需添加。
